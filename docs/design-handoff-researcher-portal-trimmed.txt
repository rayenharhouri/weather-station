# New surface: Researcher API portal

WeatherHub is a university research project at heart. The pages we've been designing are the operations surface — for admins and viewers monitoring stations day-to-day.

I also need a separate surface for researchers — academics at ENIT / ESPRIT / INSAT who want programmatic data access for their analysis and papers. Conceptually: "WeatherHub Console" (ops) vs "WeatherHub for Research" (data + APIs). Different mental model, different chrome, different default landing page. Researchers shouldn't see the alerts panel; admins shouldn't see the API console.


# What it includes

- API tokens — generate, name, expire, revoke per researcher
- Endpoint documentation — every REST route + the SSE stream, with auth, params, and example payloads
- Query playground — pick a station / metric / time range / interval, see the response inline, copy as curl / Python / R
- Bulk export — CSV, JSON, maybe Parquet; sync for small queries, async for large
- Per-token usage and rate-limit visibility
- Possibly: dataset citation strings / DOIs, public sample data, cross-tenant access for multi-campus studies


# Carry over everything we've locked


The researcher portal inherits all of this. What changes is structure and information architecture, not the visual language.
